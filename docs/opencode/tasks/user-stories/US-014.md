# US-014 — Soporte básico: Historias de usuario y criterios AC-014-NN

## Alcance general

Slice 014 — Soporte básico. El propietario crea tickets para solicitar soporte veterinario o administrativo; el admin interno consulta y gestiona dichos tickets con cambio de estado.

---

## Historias US-014-NN

### US-014-01: Propietario registra una nueva solicitud de soporte como ticket (AC-014-01)

> Como propietario, quiero registrar una solicitud de soporte para que la clinica reciba mi caso y lo atienda en el menor tiempo posible.

**Criterios AC-014-01**

- Dado un propietario con sesion activa → Cuando envia formulario con campo titulo obligatorio + descripcion opcional + categoria optiva → Que cree ticket con status=iniciado, clinic_id=la suya y user_id=su owner.id.
- El ticket creado debe tener fecha created_at en UTC; no se permite duplicar mismo titulo dentro de una ventana de 24 horas por el mismo propietario.
- Si el titulo es vacio o <5 caracteres → POST devuelve 400 con mensaje claro "El título debe contener al menos 5 caracteres".
- Backend genera y retorna 201 JSON con TicketRead completo incluyendo id, status=iniciado, category_id=NULL si no se proporcionó.
- frontend muestra EmptyState o toast de exito sin exponer internals HTTP ni stack traces.

### US-014-02: Propietario consulta sus propios tickets en una lista paginada y filtrada por estado (AC-014-03, AC-014-09)

> Como propietario, quiero ver mis solicitudes de soporte para saber en qué estado estan.

**Criterios AC-014-03, AC-014-09**

- GET /api/v1/tickets?page=1&page_size=N&status=<enum?> retorna paginacion con meta {page, page_size, total, pages}.
- Si status es pasado, la lista se filtra por ese valor; si no → todas los statuses del propietario/clinica.
- page_size debe estar en [5..100]; fuera de rango devuelve 422.
- frontend renderiza tabla/lista con titulo, estado y fecha creacion.
- Si el listado es vacio → se muestra EmptyState centrado "Sin solicitudes de soporte registradas".

### US-014-03: Propietario visualiza detalle de un ticket propio (AC-014-04)

> Como propietario, quiero ver los detalles de cada solicitud para saber el progreso de mi caso.

**Criterios AC-014-04**

- GET /api/v1/tickets/{id} retorna TicketRead completo si el id corresponde a un ticket del usuario autenticado.
- Si ID pertenece a otro propietario/clinica → 404 seguro (sin revelar existencia o datos).
- response incluye id, title, description, status, category (objeto con id+name cuando existe, null cuando no), user_name, clinic_name, created_at, updated_at.

### US-014-04: Admin interno actualiza el estado de un ticket existente (AC-014-05)

> Como admin/veterinario interno, quiero cambiar el estado de una solicitud para reflejar el avance.

**Criterios AC-014-05**

- PATCH /api/v1/tickets/{id}/status requerira Bearer de admin/interno_user con clinica matching del ticket.
- Transiciones validas: `iniciado → pendiente | proceso`, `proceso → completado | cerrado`.
- Si el usuario no es admin (es un owner intentando cambiar estado) → 403.
- Si transicion fuera de secuencia permitida → 422 con detalle "Transición inválida de X a Y".
- response {ticket_id, old_status, new_status}.

### US-014-05: Admin consulta listado de tickets de su clinica con filtros (AC-014-03 modificado)

> Como admin interno, quiero consultar todos los tickets de la clinica para priorizarlos.

**Criterios AC-014-03 modificada**

- Admin interna obtiene listados paginados similares a US-014-02 pero filtrados por clinic_id del token (no solo su user_id).
  - Mismos query params y limites de paginacion.
  - Filtro status opcional se comporta igual.
  - La lista incluye campos adicionales: owner_name y email si aplican para facilitar contacto.

### US-014-06: Obtener listado activo de categorias disponibles (AC-014-02, AC-014-06)

> Como usuario, quiero ver las categorías disponibles antes de crear un ticket; y en el detalle consultar la categoria asignada o nula.

**Criterios AC-014-02, AC-014-06**

- GET /api/v1/tickets/categories retorna lista de categorias activas para la clinica del token: {id, name, active}.
- Cada categoria es unica por (clinic_id, name). Hay seed minimo de 3 items.
- Detail endpoint (GET /tickets/{id}) incluye propiedad `category` con objeto null o un item {id, name} cuando se asigno una.

---

## Seguridad y permisos (AC-014-07, AC-014-11)

### AC-014-07: Todos los endpoints requieren Bearer token valido

- Sin bearer → 401.
- Bearer invalid/expired → 401.
- Consistente con la politica de auth de slices previos (BE-002, BE-013).

### AC-014-11: IDOR/BOLA — aislamiento por clinica/tenant

- Un propietario o admin de clinica A no puede listar ni acceder a tickets de clinica B.
- Intentos de acceso cruzado retornan 404 (sin revelar existencia).
- Creacion siempre usa tenant del token autentico; no recibe clinic_id desde el request body.

---

## Reglas de negocio resumidas

1. Titulo obligatorio, minimo 5 caracteres y maximo 200.
2. Description max 2000 chars (opcional). Categoria optiva → NULL en DB si ausente.
3. Status enum: [iniciado, pendiente, proceso, completado, cerrado]. Transiciones limitadas al update-status endpoint.
4. Unico por clinica para categoria name. Duplicado de titulo entre mismo owner y misma dia → impide creacion (constraint/check).
5. Propietario crea tickets solo de su propia clinica. Admin puede ver toda la clinica. Cambios de estado solo autorizados para admin del sistema interno o roles de clinica especifica.
