# 11 - ChatGPT Project Context

## Purpose

This document is a compact source of truth for using InVet inside ChatGPT or similar assistants.
It explains the operating model, agent structure, commands, workflow, and expected outputs.

## Project summary

InVet uses a sequential, slice-based operating model.
Each slice is vertical and must stay aligned across backend, frontend, and QA:

```text
BE-00X + FE-00X + QA-00X = one verifiable functional slice
```

The project is intentionally constrained to MVP scope.
Do not introduce products, marketplace, cart, checkout, service payment gateway, electronic invoicing, or fiscal stamping into MVP.

## Core operating model

Work is organized through OpenCode agents and slash commands.
The standard lifecycle for a slice is:

```text
/plan-task BE-00X
/implement-backend-task BE-00X
/implement-frontend-task FE-00X
/qa-task QA-00X
/review-slice BE-00X
/review-slice FE-00X
/implement-findings BE-00X
/implement-findings FE-00X
/clean-architecture-review
/security-review
/run-checks
/update-docs
```

General rules:
- Always start from a backend slice ID `BE-00X`.
- Keep backend, frontend, and QA aligned by index.
- Backend defines contracts first.
- Frontend consumes the contract of the same slice.
- QA validates the full slice.
- Reviews, checks, and documentation must be closed before advancing.

Skill usage rule:
- The available Codex skill is `customize-opencode`.
- `invet-backend-implementer`, `invet-frontend-implementer`, and the other `invet-*` names are OpenCode agents, not Codex skills.
- Invoke them through slash commands such as `/implement-backend-task BE-00X`, not as `Skill invet-backend-implementer`.

## Agent structure

### Primary orchestration

`invet-orchestrator`
- Mode: `primary`
- Objective: coordinate the complete slice flow and prevent skipping gates.

### Planning

`invet-product-planner`
- Mode: `subagent`
- Objective: translate a `BE-00X` task into an actionable MVP slice plan in `docs/opencode/plans/BE-00X-plan.md`.
- Output: objective, MVP scope, out-of-scope, entities, business rules, endpoints, frontend components, QA cases, risks, Definition of Done, and numbered checklist with measurable acceptance criteria and `Paralelismo[P]`.

### Implementation

`invet-backend-implementer`
- Mode: `all`
- Objective: implement pending backend tasks from the plan using FastAPI, SQLAlchemy 2.0, Alembic, Pytest, and Clean Architecture.
- Expected areas: entities, use cases, repositories, ORM, migrations, schemas, routers, tests, `/api/v1`.
- Marks plan tasks as complete only after acceptance criteria are verified.

`invet-frontend-implementer`
- Mode: `all`
- Objective: implement pending frontend tasks from the plan using Next.js, TypeScript, React, and Tailwind.
- Expected areas: routes, layouts, components, forms, validation, API client, UX states, tests.
- Marks plan tasks as complete only after acceptance criteria are verified.

### Validation and review

`invet-qa-validator`
- Mode: `all`
- Objective: validate the slice using plan objectives and acceptance criteria, create or adjust tests when needed, execute available tests, validate happy path, negative path, permissions, IDOR/BOLA, regression, and evidence.
- Expected artifact: QA evidence in Markdown with traceability to plan tasks, completed QA validation tasks marked in the plan, and a findings file when execution or configuration blocks occur.

`invet-slice-reviewer`
- Mode: `all`
- Objective: review plan plus implementation across BE, FE, and QA for the same slice.
- Use when: you need a targeted review before architecture/security global gates.
- Expected artifact: `docs/opencode/reviews/BE-00X-review.md` based on `docs/opencode/templates/review_findings_template.md`.

`invet-findings-implementer`
- Mode: `all`
- Objective: implement review findings, close corrections, and document the result.
- Expected artifact: `docs/opencode/reviews/BE-00X-corrections.md` based on `docs/opencode/templates/corrections_checklist_template.md`.

`invet-clean-architecture-reviewer`
- Mode: `subagent`
- Objective: verify backend layering and frontend modular separation without modifying code.

`invet-security-reviewer`
- Mode: `subagent`
- Objective: verify OWASP concerns, permissions, IDOR/BOLA, token handling, logging, and data exposure without modifying code.

### Operational support

`invet-check-runner`
- Mode: `all`
- Objective: run backend and frontend checks and summarize actionable failures.

`invet-docs-updater`
- Mode: `all`
- Objective: update Markdown documentation after the slice is implemented and validated.

## Command structure

`/plan-task BE-00X`
- Agent: `invet-product-planner`
- Produces `docs/opencode/plans/BE-00X-plan.md`.
- The plan includes numbered checklist tasks with objective, acceptance criteria, and `Paralelismo[P]`.
- No source code changes.

`/implement-backend-task BE-00X`
- Agent: `invet-backend-implementer`
- Implements only pending backend tasks from `docs/opencode/plans/BE-00X-plan.md`.
- Marks completed backend tasks as `- [x]` only after criteria are verified.

`/implement-frontend-task FE-00X`
- Agent: `invet-frontend-implementer`
- Implements only pending frontend tasks from `docs/opencode/plans/BE-00X-plan.md`.
- Marks completed frontend tasks as `- [x]` only after criteria are verified.

`/qa-task QA-00X`
- Agent: `invet-qa-validator`
- Validates backend, frontend, and integration for the slice.
- Uses plan objectives and acceptance criteria to derive QA cases.
- Creates or adjusts tests when needed and executes available tests.
- Marks completed QA validation tasks as `- [x]` only after evidence exists.
- Writes `docs/opencode/qa/QA-00X-findings.md` when environment or execution issues block QA.

`/review-slice BE-00X` o `/review-slice FE-00X`
- Agent: `invet-slice-reviewer`
- Reviews the plan and implementation of the slice.
- Creates a Markdown findings report if corrections are required.

`/implement-findings BE-00X` o `/implement-findings FE-00X`
- Agent: `invet-findings-implementer`
- Fixes the findings raised by the slice review for the same vertical slice.
- If invoked with `FE-00X`, it derives the matching `BE-00X` and keeps the same slice index.
- Creates a Markdown corrections report and checklist.

`/clean-architecture-review`
- Agent: `invet-clean-architecture-reviewer`
- Global architecture gate.

`/security-review`
- Agent: `invet-security-reviewer`
- Global security gate.

`/run-checks`
- Agent: `invet-check-runner`
- Runs tests, lint, typecheck, and build when available.

`/update-docs`
- Agent: `invet-docs-updater`
- Updates task state, risks, decisions, and related documentation.

## Workflow expectations

### Per-slice execution

1. Plan the slice from `BE-00X`.
2. Implement backend first.
3. Implement frontend against the same slice contract.
4. Execute QA for the same index.
5. Review the full slice and document findings if needed.
6. Implement findings and document closure.
7. Pass architecture review.
8. Pass security review.
9. Run checks.
10. Update documentation.

### Gate expectations

After planning:
- MVP scope is clear.
- Out-of-scope is explicit.
- Backend and frontend contracts are defined.
- QA scope is identified.
- `docs/opencode/plans/BE-00X-plan.md` exists with numbered checklist tasks, measurable acceptance criteria, and `Paralelismo[P]`.

After backend:
- API stays under `/api/v1`.
- Routers do not contain business logic.
- Domain is framework-independent.
- Repositories are abstracted.
- Tests exist when applicable.
- Backend plan tasks are marked complete only when acceptance criteria are verified.

After frontend:
- Routes and components are implemented.
- API consumption is centralized.
- UX states exist: loading, error, empty, success.
- Private routes are protected when applicable.
- Frontend plan tasks are marked complete only when acceptance criteria are verified.

After QA:
- QA cases are derived from plan objectives and acceptance criteria.
- Happy path validated.
- Negative path validated.
- Permissions and IDOR/BOLA validated.
- Regression minimally covered.
- Evidence recorded.
- Evidence is traced back to plan tasks.
- Test creation/execution documented.
- QA blockers documented in Markdown if the environment prevented execution.

Before moving to the next slice:
- Review findings are closed or explicitly accepted.
- Architecture review is approved.
- Security review is approved.
- Checks are green or failures are documented.
- Documentation is updated.

## Guidance for ChatGPT usage

When using this project as context in ChatGPT:
- Treat `docs/opencode/tasks/**` as the primary functional source for each slice.
- Preserve the same index across BE, FE, and QA.
- Do not expand scope beyond MVP unless explicitly requested.
- Prefer backend-first implementation.
- Always reason about permissions, data exposure, and IDOR/BOLA.
- Respect Clean Architecture boundaries.
- Document findings and corrections in Markdown rather than leaving them implicit.
